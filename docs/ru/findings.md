# Находки

Разбор `tg://companion` в Telegram-iOS: что именно ломается, на каких числах и при каких условиях. Объект — `TelegramMessenger/Telegram-iOS`, HEAD `24638bc69b` (2026-11-03), коммит-источник `44681a28` «Experiment».

Все числа взяты из `FACTS.md` и не округлены. Где значение получено арифметикой, а не замером, это сказано прямо. Ссылки на отчёты (`01-scope.md`, `verify/C02a`) — пути в архиве аудита, а не файлы этого репозитория.

Автор: **nimo** ([@Kkuwkl](https://github.com/Kkuwkl)) · опубликовано 2026-11-16.

## 1. Путь до экрана

| Шаг | Где | Что происходит |
|---|---|---|
| 1 | `submodules/TelegramUI/Sources/OpenUrl.swift:395-404` | Точное сравнение: `scheme == "tg" && host == "companion"` |
| 2 | Там же, `:397-399` | push в `rootController` — без диалога и без подтверждения |
| 3 | `Components/DebugCompanionScreen` | Экран поднимается целиком: Metal, каталог, шейдеры |
| 4 | `CompanionCatalog.swift:59-91` | Резолв `tttt3dexample` и поиск документов в канале |
| 5 | `DebugCompanionScreen.swift:340-343` | Скачивание выбранного пресета из канала |

Гейтов нет ни на одном шаге: `#if DEBUG` — ноль вхождений в цепочке, runtime-флага нет, `testonly` в `BUILD` нет. Линковка безусловная: `TelegramUI/BUILD:442`, `Telegram/BUILD:1887,986`. Схема `tg` объявлена в `Info.plist` без условий.

**Два тапа, а не один.** Первый показ всегда берёт встроенный (бандловый) ассет: пресет «1» — четыре файла из `CompanionResources.bundle`, `isBundled == true`. Сетевой контент требует второго тапа по чипу, и на этом чипе нет ничего, кроме цифры: `"\(index+1)"`, `:518`. Название пресета попадает только в `accessibilityLabel` (`:525`), то есть видно лишь VoiceOver. Ни имени файла, ни источника, ни размера, ни даты, ни подтверждения.

**Passcode не обходится.** Слой блокировки выше по z-порядку, экран уходит под него. Но экран не снимается: `AppLock.dismiss` бьёт по `WindowRootViewController`, а не по `TelegramRootController`. Под локом продолжают идти `newLibraryWithSource` на главном потоке и `catalog.load()`; после разблокировки экран интерактивен без действий пользователя. Это отложенный спуфинг, а не обход блокировки.

Source: `FACTS.md` §«Точка входа»; `07-swift-entry.md` A7-1/A7-2; `16-verify-reachability.md` п. 1–2; `verify/C04b` §2, `C06a`/`C06b`.

## 2. Находка 1 — краш в обработке ошибок

Файл `716–952 байта`. Ни CVE, ни структур памяти, ни таймингов: детерминированный краш на пути, который должен был показать тост.

### Механика

1. `Sources/CompanionRenderer.mm:13` — единственная конверсия `std::string → NSString` во всём таргете: `[NSString stringWithUTF8String:]` внутри литерала `NSDictionary`.
2. Невалидный UTF-8 приходит из внешних полей: `giftNode.id`, `giftSlot`, `sockets[].node`, `GIFT_animation_binding.node`.
3. Конверсия возвращает `nil`, литерал с `nil`-значением бросает `NSInvalidArgumentException`.
4. Исключение рождается **внутри C++ `catch`**, где уже обрабатывается ошибка загрузки. `@try` в таргете — 0 вхождений, `NSSetUncaughtExceptionHandler` — 0.
5. Swift ловит только `NSError`, не `NSException`. Процесс убит, тоста нет.

Краш сидит в `errorFor`: четыре вызова (`:89, :157, :175, :213`). Строки приносят семь throw-сайтов: `CharacterInstance.cpp:15, 25, 37, 74, 165, 172, 189`.

```objc
// схема, Sources/CompanionRenderer.mm:13
[NSString stringWithUTF8String:ex.what()]   // невалидный UTF-8 → nil
@{ @"key": <этот nil> }                     // литерал → NSInvalidArgumentException
```

### Воспроизведение

| Стенд | Файл | Результат |
|---|---|---|
| C02a | 716 Б — два `giftNode.id` с байтом `0xFF` | Исключение на неизменённом коде, вплоть до `errorFor` |
| C02b | 860–952 Б — исправленный `.animation.glb`, `{"version":1,"node":"A\xff"}` | То же; разница ровно в одном байте |
| C02a | `giftSlot` в `.materials` или строка в `GIFT_animation_binding` | Не триггер: расширение должно быть объектом, не строкой |

`errorFor` не «спуфинг текста»: это самостоятельная точка краша, причём на файле, который защита **правильно** отвергла. Краш не зависит от памяти, ASLR и таймингов, поэтому стоит выше четырёхгигабайтных амплификаций по цене входа.

Source: `FACTS.md` §«Что входит в публичную версию», п. 1; `verify/C02a` §4, `C02b` §4–5.

## 3. Находка 2 — амплификация

Общий корень: лимиты пообъектные, а произведение не ограничено. Все четыре файла проходят штатные гейты (32 МиБ, `count ≤ 1e6`, `validateCage`) и дополнительно прогнаны через нетронутый бинарь B3 со `status: "ok"`.

| Механизм | Файл | Результат | Время | Где |
|---|---|---|---|---|
| Индексы: лимит на примитив, не на модель | 2,35 МиБ (2 460 632 Б) | 607,9 МиБ CPU; `Σ p.indices` 614 400 000 Б = 585,9 МиБ; 153,6 млн элементов; GPU ≈1,23 ГБ | 1,62–2,02 с | `GiftModel.cpp:321-326, 385, 388`; `CompanionRenderer.mm:131` |
| 64 разных PNG в RGBA8 | 3,63 МиБ (3 806 732 Б) | 4,0 ГиБ (4 294 967 296 Б), пик 4162,9 МиБ | 15,99 с | `CompanionRenderer.mm:42, 92, 114-116, 142` |
| `images[]`: копия всего `bufferView` | 32 МиБ (33 554 432 Б) — ровно гейт | 2115 МиБ (`Σ` 2 147 202 304 Б) | memcpy 1,89 с, всего 2,29 с | `GiftModel.cpp:170-177` (`:177`) |
| Скины: `floats()` внутри цикла по `skins_count` | 1,0 МиБ (1 053 600 Б) | пик 67,0 МиБ, 85,9 мс на скин, churn 131 ГБ | 175,871 с на главном потоке | `GiftModel.cpp:286-289, 19-21` |

Детали, без которых числа читаются неправильно:

- **Индексы.** Один `{"indices": 0}` × 128 примитивов; лимит стоит на примитив, а не на модель. Вершины бюджетируются (`totalVertices ≤ 200 000`), поэтому сценарий «1,2 млн × 128» невозможен — работает именно произведение индексов.
- **Текстуры.** Нужны 64 разных набора байт. Кэш ключуется содержимым (`std::map` по вектору байт), поэтому 64 записи `images[]` на один `bufferView` дают один декод и 126,6 МиБ, а не 4 ГиБ.
- **`images[]`.** 64 записи на один и тот же `bufferView` размером ровно 32 МиБ. Валидный PNG не нужен: декодирования на этом шаге нет, только копирование диапазона. Контроль на 8 записях — 256,0 МиБ, то есть линейность подтверждена.
- **Скины.** 2048 скинов, `count = 1e6` ровно на границе, `byteStride = 1` проходит `cgltf.h:1610`. Защита «по памяти» не срабатывает, потому что оружие здесь — время.

Сумма потолков по одному файлу (≈5,3 ГиБ) — арифметика, а не единый замер: измерены 2,0 ГиБ, 4,0 ГиБ и 586 МиБ по отдельности, вместе — нет. Так и подаём.

Source: `FACTS.md` §«Что входит в публичную версию», п. 2; `verify/C03` §1–5; `CHAINS.md` §2.

## 4. Находка 3 — модель доверия

Каталог привязан к имени, а не к пиру. `resolvePeerByName("tttt3dexample")` возвращает `peerId`, но выборка документов от него не зависит.

| Что должно проверяться | Что проверяется | Следствие |
|---|---|---|
| `peerId` + `accessHash` канала | Ничего: резолв по имени | Смена владельца молча меняет код в процессе |
| Тип пира — `TelegramChannel` | Ничего: `case .channel` отсутствует | Каталогом становится группа с открытым постингом или личный чат |
| `documentId` + SHA-256 | Только суффикс `.glb` и 32 МиБ | Подмена файла под тем же именем не видна |
| Свежесть записи | TTL 48 ч (`ageLimit = 172 800` с) | «Тёплый» клиент до двух суток ходит в старый канал |

Механика подмены: `messages.search` возвращает историю канала, и «последнее сообщение с тем же именем побеждает» (`CompanionCatalog.swift:85-91`). Достаточно одного поста, чтобы перекрыть компонент, не удаляя предыдущий, — UI при этом не меняется.

Отдельно: username **не входит в адрес пира**. Адрес — пара `(id, accessHash)`, поэтому «тёплый» клиент продолжает читать старый канал, а «холодный» переключается сразу. Инвалидации по смене имени нет: `resolvedByNamePeers` встречается ровно в трёх местах — чтение, запись и объявление.

`@tttt3dexample` — публичный канал: писать в него подписчик не может. Поэтому модель доверия ломается не «любым желающим», а тем, кто получил контроль над каналом или над username. Это же условие снимает половину громких формулировок: без контроля остаётся self-DoS.

Source: `FACTS.md` §«Что входит в публичную версию», п. 3; `08-dataflow-catalog.md` A8-01…A8-04; `verify/C05a` §4, `C08`.

## 6. Смежные наблюдения

Не входят в четыре главные находки, но нужны, чтобы картина не выглядела уже, чем она есть.

- **Палитра скелета (F-01).** `inverseBindMatrices->count` не сверяется с `joints_count` (`GiftModel.cpp:289-293`): при `joints_count=256, count=1` ASan показывает `heap-buffer-overflow READ of size 64`, в палитру попадает 16 320 Б мусора. Эффект визуальный: схлопнутая или невидимая модель, 0 падений на 400 релизных прогонов. Подаём как «доказанный дефект памяти с ограниченным эффектом», не как краш.
- **Бюджеты OpenSubdiv стоят после работы (F-10/F-25).** Клетка 4096×16 = 65 536 углов проходит `validateCage`; `RefineAdaptive` и `PatchTableFactory::Create` дают ~1 048 576 патчей, и только потом срабатывает `patches ≤ 30000`. Объём не измерен, но работа уже сделана.
- **Память покрытого экрана (F-27).** Render targets освобождаются только в `dealloc`: 39–44 МБ на экран, который хоть раз показался. `didReceiveMemoryWarning` не реализован.
- **Устаревание вендора (F-17).** `cgltf` запинен на `85cd6238` (v1.15-11) и не обновляется; upstream-фикса нет, PR открыт. Процесса обновления тоже нет: три разные схемы `SOURCE.json`, ни `VENDOR.md`, ни тестов.

Source: `verify/C01b` §4–5; `verify/C08`; `verify/C04b` §5; `09-build-supplychain.md` A9-01.

## 7. Что это не доказывает

- Нет выполнения кода: ни удалённо, ни локально без записи в подписанный `.app`.
- Нет доступа к переписке, ключам, камере, микрофону, деньгам: в первопартийном коде нет клиента «наружу» и нет записи на диск.
- Нет обхода passcode: экран живёт под локом, но лок не снимает.
- Нет «одного тапа до чужого `.glb`»: сетевой контент — второй тап по чипу с цифрой.
- Нет атаки без контроля канала или username: иначе только self-DoS.
- Нет устройства и Xcode: пороги jetsam и Foundation-звено `errorFor` остаются выводами по коду и контракту API.

Source: `FACTS.md` §«Что публично НЕ утверждать».
